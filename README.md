# 优衣库（中国区）商城 · 商品库与价格监控

本地个人自用工具。把优衣库官网（uniqlo.cn）当作一个商城来浏览：**瀑布流商品库 + 官方分类导航
+ 新品区 + 历史价格 + 变价信息**；对关注商品做**颜色 × 尺码库存**与**价格变化**监控，
断货 / 补货 / 低库存 / 降价时推送通知。

> 数据来源为官网公开接口（实测，无需登录）。库存为**全国快递仓可售量**，与收货地区无关
> （已实测：换任何城市参数，库存零变化）。数值平台封顶 20，>20 均显示 20。

## 两个跟踪层级

| 层级 | 采集内容 | 上游成本 | 谁是这个层级 |
|---|---|---|---|
| `catalog` 商品库 | 列表页字段：价格 / 图片 / 色卡 / 分类 / 新品尝鲜 | 全站一趟 ≈ 78 次请求（6 小时一轮） | 全站约 1700 件商品 |
| `full` 关注中 | 详情 + 尺码库存：颜色×尺码在售件数、在途 | 每商品 2 次请求（30 分钟一轮） | 你点过「关注降价」或在监控页添加的商品 |

**为什么不能全站都做尺码监控**：尺码库存必须走「详情 + 库存」两跳，全站 ~1700 件按 30 分钟采一轮
需要 ≈ 3400 次/半小时的请求，会直接触发官网风控。所以商品库只跟价格，关注后才升级为全量采集；
未关注商品也能在详情里点「拉取尺码库存」按需拉一次（单次 3 次请求，不进监控）。

## 启动

```bash
# 依赖（已验证版本：fastapi 0.115.14 / uvicorn 0.52.1 / httpx 0.28.1）
pip install -r requirements.txt

python app.py
# 打开 http://127.0.0.1:8811
```

首次启动会自动在后台建库（约 1–2 分钟，也可到「设置 → 立即扫描商品库」手动触发）。

数据存于 `data/monitor.db`（SQLite 单文件，可随时备份/删除）。

环境变量：`UQ_HOST`（默认 `127.0.0.1`，容器中设为 `0.0.0.0`）、`UQ_PORT`（默认 `8811`）、
`UQ_DB`（自定义数据库路径，便于用副本库做验证）、`UQ_NO_STARTUP_SWEEP=1`（关闭启动自动建库）。

## Docker 部署（支持 amd64 / arm64）

镜像由 GitHub Actions 自动构建并推送至 `ghcr.io/fanmu95/uniqlo-monitor:latest`，
同时提供 `linux/amd64` 与 `linux/arm64` 两个架构（NAS 会自动选择匹配的架构）。

```bash
# NAS / 服务器
docker compose up -d          # 使用仓库中的 docker-compose.yml

# 或手动运行
docker run -d --name uniqlo-monitor \
  -p 9903:8811 \
  -e TZ=Asia/Shanghai \
  -e UQ_HOST=0.0.0.0 \
  -v $(pwd)/data:/app/data \
  --restart unless-stopped \
  ghcr.io/fanmu95/uniqlo-monitor:latest
```

**注意事项**

- `TZ=Asia/Shanghai` 必须设置：否则容器内为 UTC，免打扰时段（23:00-08:00）判断会错 8 小时
- 数据目录务必挂卷：SQLite 数据库、价格历史、订阅与通知配置都在 `/app/data`
- 端口映射左侧（`9903`）是对外端口，可自行修改
- ghcr 包若为私有，拉取前需 `docker login ghcr.io`，或在 GitHub 包设置页改为公开
- 容器需可访问 `www.uniqlo.cn`（接口与商品图片）

## 使用

### 商城（瀑布流浏览）

1. **浏览**：首页是官方商品库的瀑布流（当前约 1700 件），滚动到底自动加载下一页。
   卡片显示：主图、名称、现价 / 原价 / 折扣、以及 新品 · 限时特优 · 超值精选 · 可改裤长 · 已关注 等官方标识。
2. **分类**：分类导航来自**官方分类树**，共 **4 级**（L1 6 个 / L2 57 / L3 265 / L4 926）：
   男装 / 女装 / 童装 / 婴幼儿 / UNIQLO TOP 五个一级 → 系列 → 品类 → 细分，
   逐级点选下钻（点 L1 出系列行，点系列出品类行，点品类出细分行），每个 chip 带件数；
   顶部面包屑可点任意一段回退，「↑ 上级」回上一层。商品同时挂在它的各级祖先分类上，
   所以任何一层都能筛（例如 男装 › 外套 › 休闲外套 › 休闲茄克 = 19 件）。
   商品↔分类关联取自官方列表条目自带的 `cateSequence` 字段，不额外请求。
3. **新品**：`rank=newest` + `identity=["new_product"]` 抓到的官方「新作商品」榜（约 220 件），
   点「只看新品」可只看新品。
4. **筛选 / 排序 / 搜索**（都是本地条件，0 上游请求，可任意叠加）：
   - 开关：只看新品（官方「新作商品」榜 219 件）· 只看打折（现价 < 原价，682 件）·
     限时特优（官方标识，82 件）
   - 折扣档位：不限 / ≥20%（661 件）/ ≥30%（462 件）/ ≥50%（248 件）
   - 排序：官方推荐 / 最新上架 / 新品优先 / 价格升降 / 折扣力度
   - 搜索：商品名或 6 位编号，可与分类、开关、档位、排序叠加
   - 接口另有 `only_stock`（官网 `stock=Y`）：实测官方列表只收可购商品、恒为 Y，界面未放出
5. **商品详情**（点卡片）：大图 + 色卡（点色卡换图）、**历史价格曲线**、变价记录、
   颜色 / 尺码区间，以及「关注降价 / 设置预期价 / 拉取尺码库存 / 官网页面」。
   曲线支持：**时间范围**（全部 / 90 天 / 30 天）· **限时特优时段**红色底色（从开始记录起积累）·
   **月度低点**绿圈标注。

### 关注与监控

6. **关注降价**（卡片右上角或详情页）：把该商品从商品库升级为全量监控 ——
   立即采集一次尺码库存，此后每 30 分钟跟价与跟库存；降价 / 达标按预期价规则推送。
   「关注」= 价格订阅，**不会**因为任意尺码补货刷屏（整商品订阅不订阅库存事件）。
7. **尺码订阅**：在详情「拉取尺码库存」后点色码单元格，订阅该「颜色 + 尺码」；
   订阅后**仅这些尺码**的断货 / 补货 / 低库存才推送。
8. **预期价**：设置后：未达预期只记录不推送；现价 ≤ 预期价 → 推「达标」；
   价格回升越过预期 → 状态复位，再次跌破时再推一次；清除则恢复「降价即推送」。
9. **变价信息**：全站商品的价格变动流（1/3/7/30 天，可只看降价或涨价），点条目直接进详情。
10. **变更日志**：关注商品的库存 / 价格事件明细 + 采集日志。
11. **通知**：设置中开启。支持 PushPlus / ntfy / 企业微信机器人，支持免打扰时段（默认 23:00-08:00）。
    另有三个细化开关：**通知类型**（降价 / 达标 · 补货 / 断货 / 低库存 · 在途 · 下架，四组独立）·
    **降价推送阈值**（降幅小于 N% 只记录不推送；达标通知不受影响）· **保留策略**（事件 90 天、采集日志 30 天）。
12. **删除商品的影响**：会一并移除该商品的价格历史；**订阅记录保留**，
    重新添加同一商品时订阅自动恢复，价格曲线从新监控周期重新开始（史低同时重置）。

### 下架怎么处理（数据时效说明）

数据是「本地快照 + 周期扫描」，不是实时：

| 数据 | 刷新周期 | 可调 |
|---|---|---|
| 商品库（价格 / 是否在售 / 新品 / 分类） | 6 小时一轮全站 | 设置页「商品库扫描间隔」 |
| 关注中商品（颜色×尺码库存） | 15~30 分钟 | 设置页「库存采集间隔」 |

- 判定口径：**连续 N 天（默认 3）未在官网分类列表出现** → 标记为已下架（`products.gone_ts`）。
  只在**一轮扫描完整扫完（或续扫补齐）**时判定，半途中断不会误判。
- 分类树同步完整时，会清理「官方已下线且没有任何商品挂靠」的分类节点（留 1 天宽限，
  本轮有请求失败则不清理）。
- 已下架商品：商城列表 / 变价流 / 新品榜统一隐藏；关注商品会打「已下架」标记、
  **暂停自动采集**（不再每轮无效请求），并发一条 `GONE 下架` 通知；
  详情页显示红字说明并禁用订阅 / 拉取尺码（保留「取消关注」便于清理）。
- **重新上架自动恢复**：下一轮扫描见到该商品即清空 `gone_ts`，自动恢复监控。
  想立刻核对可点关注卡片的「刷新」（强制请求一次，但状态仍以扫描结果为准）。
- 详情页的「最后在售 / 抓取时间」标注可直接看出数据新鲜度。

### 历史最低价的口径

- **史低 = 我们观察到的最低价**，不是官方全周期最低（官网不提供历史价，只能从开始扫描那天算起）
- 商品库商品随**全站扫描**（默认 6 小时）用列表价更新；关注商品随**库存采集**（15~30 分钟）用详情价更新
- **只降不升**：价格回涨时史低不动；下一轮扫描跌得更低时继续下探
- 不变式：史低必须等于价格历史里的最低点，每轮扫描后自愈对齐（旁路榜单如新品榜不改已存在商品的价格）
- 采样是离散的：两次扫描之间的短暂降价可能漏检（关注中的商品 15 分钟一采，漏检概率低得多）
- 删除商品会同时清空价格历史，重新添加则史低从新周期重新开始

### 频率与开关（设置页）

- **商品库扫描间隔**（默认 360 分钟）：全站翻页 ≈ 78 次请求，1 req/s 限速 ≈ 1.5 分钟；
  **断点续扫**：某轮中途失败会记下页码，12 小时内的下一轮从该页续扫并补齐（两轮合起来覆盖全站）；
  只有覆盖全站的一轮结束时才做下架判定与史低自愈
- **库存采集间隔**（默认 30 分钟）：只跑「关注中」的商品
- **价格历史保留**（默认 90 天）、**下架隐藏天数**（默认 3 天未在扫描中出现即从商城隐藏）
- **立即扫描商品库**：手动触发一轮全站扫描 + 新品榜 + 分类同步

## 事件类型

| 事件 | 触发条件 | 是否推送 |
|---|---|---|
| 补货 IN | 该尺码库存 0 → >0 | 仅订阅命中的尺码推送 |
| 断货 OUT | 该尺码库存 >0 → 0 | 仅订阅命中的尺码推送 |
| 低库存 LOW | 库存 ≤ 阈值（默认 2 件） | 仅订阅命中的尺码推送 |
| 在途 TRANSIT | 当前断货但在途有货 | 仅订阅命中的尺码推送 |
| 降价 PRICE_DOWN | 较上次监控降价 | **未设预期价时推**；设了且未达预期 → 仅记录 |
| 达标 TARGET_HIT | 现价 ≤ 预期价 | 推（复位后可重复触发） |
| 涨价 PRICE_UP | 较上次监控涨价 | 仅记录，不推送 |

> 「关注降价」写入的是整商品订阅（颜色/尺码为空），只订阅价格、不订阅库存事件。
> 想收补货提醒请在详情里按颜色×尺码订阅。

## 接口链路（逆向自官网，2026-09 实测有效）

```
1) POST /p/hmall-sc-service/search/searchWithDescriptionAndConditions/zh_CN
      关键词/编号 → 内部 productCode（u0000000064773）
2) GET  /h/product/i/product/spu/h5/query/{productCode}/zh_CN
      rows[] = SKU 字典（productId + size + style，注意须用 /h/ 移动端路径）
3) POST /h/stock/stock/query/zh_CN
      body {"type":"DETAIL","distribution":"EXPRESS","productCode":...}
      → skuStocks[productId] = 尺码库存
4) POST /p/hmall-sc-service/search/searchWithCategoryCodeAndConditions/zh_CN
      分类浏览：categoryCode 与官网 /c/<slug>.html 的 slug 一致（如 3msweat、4310011315）
      pageSize 服务端硬顶 25 条/页；rank=overall|newest|new|priceAsc|priceDesc|sales
      identity=["new_product"|"time_doptimal"|"concessional_rate"|"revision"|"pickUp"]
      withSideBar="Y" → resp[0] 为筛选面，其中「品类」facet 含该分类的祖先链与整棵子树
      resp[1]=商品数组（含 cateSequence 分类归属、new 时间戳、colorPic/chipPic、stock 标记）
      resp[2]={productSum, pageSize}
```

注意事项：

- 详情必须用**内部 ID**（`u` 开头），传 6 位编号会返回 `PD_PRODUCT_01`。
- 详情必须用 **`/h/` 移动端路径**，`/p/` PC 路径的 rows 里没有 size/style 字段。
- 官网会把同款不同商品码聚合展示，此时 `style` 字段退化成「任意色」，
  颜色从 `styleText`（如 `486980/32深米色`）解析，重名时显示为 `深米色(486980)`。
- **列表接口的 `productCode` 可能是「款式聚合变体」**：实测 482432 在列表里是
  `u0000000073746`（16 个 SKU），而搜索接口解析出的 `u0000000069773` 才是完整 24 个 SKU。
  因此商品库里的内部 ID 只在新入库时写入，订阅 / 拉取尺码前会用搜索接口再校验一次。
- **同一商品码可能在 ALL 列表里重复出现且价格不同**（实测 482246 分别 ¥149 / ¥99），
  一轮扫描按「首次出现」为准，重复条目跳过。
- **图片 CDN 按 TLS 指纹拦截 Python**：同一请求 curl/浏览器 200，httpx 一律 567 AccessDeny
  （换 UA / Referer / Accept-Encoding / H5 头均无效）。所以前端**直连图片 CDN**，
  后端 `/img/{path}` 代理保留作兜底（`?w=225|561|1000` 指定档位）。
- **图片档位并非都存在**：`/main/first/` 只有 561(1200px) 与 1000(2100px)，225 会 404；
  `/sku/` 的 225(480px) / 561 / 1000 都在。故默认用接口返回的原路径，仅详情大图升到 1000。
- 指定线下门店的尺码库存接口不提供；线下门店有货列表（SPU 级）在搜索接口 `stores[]` 字段。
- 分类树只认顶层码（`1111MEN` / `1111WOMEN` / `1111KIDS` / `1111BABY` / `UNIQLOTOP`）
  各请求一次即可拿到整棵子树，无需逐层展开。

## 合规提醒

官网 robots.txt 禁止通用爬虫（仅放行搜索引擎）。请保持**个人自用、低频、不公开分发数据**，
勿触碰登录态接口（购物车 / 下单 / 用户服务）。默认参数已按低频设计：全局 1 req/s 串行、
商品库 6 小时一轮、库存 30 分钟一轮，扫描只走公开列表 / 详情 / 库存接口。
